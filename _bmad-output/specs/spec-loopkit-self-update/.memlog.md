- (direction) Create a two-phase self-update path: Phase 1 detects and announces releases with manual installation; Phase 2 adds verified in-app installation and relaunch.
- (note) LoopKit already publishes a uniquely versioned universal Community DMG and SHA-256 file from successful current main builds; superseded builds do not replace the latest release.
- (note) The current Community trust model is ad-hoc signed and unnotarized, may require Gatekeeper confirmation, and may cause privacy permissions to be requested again after an update.
- (capability) CAP-1: LoopKit determines whether its installed bundle version is older than the latest eligible published release; success is a deterministic comparison result for older, equal, newer, malformed, and prerelease inputs.
- (capability) CAP-2: A user can manually check for updates at any time; success is an explicit up-to-date, update-available, or actionable failure result.
- (capability) CAP-3: LoopKit checks for updates automatically without disrupting first run or normal audio work; success is no more than one background request per 24 hours after first-run setup and no user interruption when current or offline.
- (capability) CAP-4: A user can notice and inspect an available update from normal LoopKit surfaces; success is consistent availability state in the app menu, dashboard, and menu-bar controller with version and release details.
- (capability) CAP-5: In Phase 1, a user can reach the authoritative release and complete the existing Community upgrade flow; success is a View Release handoff to the matching GitHub release with no claim of in-app installation.
- (capability) CAP-6: In Phase 2, a user can obtain, cryptographically verify, install, and relaunch into an eligible update; success is an authentic update replacing the app atomically while invalid or interrupted updates leave the installed version runnable.
- (capability) CAP-7: The release pipeline can publish updater-consumable metadata tied to the exact validated non-superseded build; success is that version, artifact URL, size, signature, compatibility, and release notes describe the same released app.
- (capability) CAP-8: Updating coordinates with LoopKit lifecycle and audio ownership; success is clear warning before interruption, clean app and XPC service shutdown, successful relaunch, and actionable recovery when installation cannot proceed.
- (decision) Automatic checks are enabled by default in Phase 1, run at most daily, and do not run during first-run setup.
- (decision) Background check failures remain quiet; manual check failures are explained with an actionable retry path.
- (decision) When current, LoopKit shows no persistent update UI; a manual check confirms the installed version is current.
- (decision) Phase 1 offers View Release and Later, with no Skip This Version control.
- (decision) Update availability uses the existing teal informational treatment; it is not a warning, error, connection fault, or setup task.
- (decision) Update behavior belongs to ControlApp app-lifecycle state and does not add audio-service or LoopKitIPC responsibilities.
- (decision) The standard macOS application menu gains Check for Updates; the dashboard top bar gains a compact version pill only when available; the menu-bar controller gains an availability action.
- (decision) A compact themed sheet presents installed and available versions, release notes, and phase-appropriate actions using existing LoopKit visual tokens.
- (decision) Phase 2 uses Sparkle 2 with EdDSA-signed updates rather than a hand-built installer.
- (decision) Phase 2 remains user-prompted initially; silent automatic installation is out of scope.
- (constraint) The updater must preserve the current Community distribution truth: ad-hoc signing is not notarization or verified-publisher identity, and UX must not imply otherwise.
- (constraint) No update flow may disable Gatekeeper, remove quarantine attributes, invoke tccutil, or promise privacy permissions will survive an update.
- (constraint) An install or relaunch can briefly stop Broadcast and Monitor audio only after the user is told and chooses an install action.
- (constraint) The existing version source remains bundle version metadata produced by the release workflow, and eligible release tags remain semantically comparable to installed versions.
- (constraint) Xcode project integration changes must be made in XcodeGen project.yml, never in generated xcodeproj files.
- (constraint) Network, parsing, comparison, caching, and presentation decisions must be independently testable without GitHub, CoreAudio, permissions, or the XPC service.
- (constraint) BlackHole remains externally owned and must never be downloaded, installed, updated, or removed by LoopKit.
- (decision) Phase 1 retains the current every-successful-main release cadence and manual Community DMG installation.
- (assumption) The twoplustwoone/loop-kit repository and its published releases remain publicly readable without application credentials.
- (assumption) Existing release tags and built CFBundleShortVersionString values continue using vMAJOR.MINOR.PATCH and MAJOR.MINOR.PATCH forms that identify the same release.
- (question) For Phase 2, must Developer ID signing and notarization become prerequisites, or must verified self-install continue to support ad-hoc Community builds?
- (question) Where will the stable Sparkle appcast be hosted, and how will its EdDSA private key be protected and made available only to trusted release jobs?
- (question) Should Phase 2 offer Install on Quit in addition to immediate Update and Relaunch?
- (direction) Do not use Stitch for Phase 1; follow native macOS update conventions and the existing LoopKit theme unless later visual exploration identifies a real gap.
- (direction) Keep Phase 1 and Phase 2 in separate pull requests so update awareness can ship before security-sensitive installation machinery.
- (capability) CAP-4 clarification: A user can notice and inspect an available update from normal LoopKit surfaces; success is that the app-menu command reaches the shared state while dashboard and menu-bar availability surfaces show the same version and release details.

- (decision) Phase 2 must support ad-hoc Community builds; Developer ID signing and notarization are not prerequisites for verified self-installation.
- (constraint) For ad-hoc Community self-updates, Sparkle EdDSA verification is the publisher-authenticity root and must remain distinct from any claim of Apple trust or notarization.
- (decision) Host the stable public Sparkle feed at https://twoplustwoone.github.io/loop-kit/appcast.xml through GitHub Pages; keep update archives as assets on their matching GitHub Releases.
- (decision) Publish the new GitHub Release before deploying its appcast so feed-deployment failure leaves clients on the previous valid feed instead of referencing an unavailable artifact.
- (decision) Embed the public Sparkle EdDSA key in ControlApp Info.plist as SUPublicEDKey; the public key is committed source and is not secret.
- (decision) Generate the EdDSA key offline; retain the private key in the maintainer macOS login Keychain and an encrypted offline backup, and store a CI copy only as the SPARKLE_EDDSA_PRIVATE_KEY secret in a release-only GitHub Actions environment restricted to current main release jobs.
- (constraint) The private EdDSA key must never be committed, published to GitHub Pages or Releases, written to logs, exposed to pull-request jobs, or persisted on the runner; CI passes it to Sparkle signing tools through standard input.
- (decision) Phase 2 signs update archives, the appcast, and release notes and enables feed-signature and pre-extraction verification supported by Sparkle.
- (note) Install on Quit means download and verify now, defer replacement until the user later quits LoopKit normally, then launch the new version on the next start; it avoids interrupting an active audio session but may remain pending because menu-bar users rarely quit.
- (direction) Recommend Update and Relaunch as the primary Phase 2 action and Install on Quit as a secondary action; keep this recommendation open until the user confirms it.
- (constraint) Because ad-hoc Community builds cannot rely on Developer ID for Sparkle key rotation, Phase 2 requires a documented key-loss and compromise recovery path; affected clients may need one manual Community update to trust a replacement key.
- (constraint) Phase 2 must use a reviewed Sparkle release new enough to support signed feeds and verification before extraction; Sparkle 2.9 is the minimum feature baseline.
